## Goal

Continue the M254.x `ImplementationBody` removal series by retiring the
remaining lowerer/private compatibility-body API surface and the obsolete
primitive-call diagnostic wrapper that still accept `ImplementationBody`
directly.

## Scope

Implement the smallest coherent retirement slice:

- Replace `Lowerer` private helpers that accept `body: ImplementationBody` with
  helpers that accept the existing fragment-first selected body token view or
  explicit token/source values.
- Remove local `ImplementationBody` construction from lowerer direct-body or
  branch helpers when an explicit token/source view can express the same
  compatibility contract.
- Remove or deprecate the old
  `unsupported_primitive_call_diagnostics(body, ...)` wrapper if no production
  caller needs it; route production and tests through
  `unsupported_primitive_call_diagnostics_from_body_tokens(...)` or a
  fragment-first selected-context path.
- Preserve token-only fallback behavior for selected implementations without
  `source_body_fragments`.
- Add focused static guardrails, likely in
  `tslgen/tests/test_m254_8_fragment_first_lowerer_compatibility_body_retirement.py`,
  proving `tslgen/src/tslgen/lowering/lowerer.py` and
  `tslgen/src/tslgen/lowering/primitive_calls.py` no longer expose private or
  public helper signatures with `body: ImplementationBody`.
- Record exact remaining `ImplementationBody` references and use that
  accounting to select the next M254.x prompt.

## Non-Negotiable Guardrails

- No discovery semantic changes.
- No new TSIL keyword semantics or keyword spellings.
- No new parser, source scanner, or source repair path.
- No pairwise surrounding-keyword handlers.
- No backend rendering, generated-project build verification, template
  rendering, CLI workflow, primitive-call selector semantics, dependency
  closure semantics, assignment/index parsing, or target-language expression
  parsing.
- Do not remove the domain `ImplementationBody` class, catalog-builder
  compatibility construction, primitive-project compatibility construction, or
  token-only tests in this milestone.
- Do not introduce runtime dependencies on `frozen` or `tslgenold`.
- Do not reactivate M255 while production body lowering still depends on
  `ImplementationBody`.

## Expected Tests

Add or update focused tests so accepted behavior remains covered:

- Existing M254.5 direct-body lowering tests should still cover fragment-backed
  selected implementations with empty compatibility body tokens.
- Existing primitive-call diagnostic/inventory tests should continue to cover
  token-only fallback and fragment preference.
- A new static guardrail should assert that `lowerer.py` and
  `primitive_calls.py` no longer define helper signatures with
  `body: ImplementationBody`, while remaining domain/catalog/pipeline
  references are still accurately classified.

## Out Of Scope

Changing lowering semantics, removing the domain `ImplementationBody` class,
removing catalog/pipeline compatibility body construction, deleting token-only
tests, backend rendering, generated-project build verification, primitive-call
selector semantics, dependency-closure behavior, source repair,
target-language parsing, fixture-shaped pipelines, runtime dependencies on
`frozen` or `tslgenold`, and M255.

If evidence shows this cannot be done safely in one coherent slice, stop
before speculative implementation and create a narrower M254.8 planning prompt.
