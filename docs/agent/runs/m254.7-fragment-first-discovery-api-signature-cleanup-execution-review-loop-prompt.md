## Goal

Continue the M254.x `ImplementationBody` removal series by removing explicit
`body: ImplementationBody` parameters from already migrated fragment-first
selected-implementation discovery APIs.

## Scope

Implement the smallest coherent API-shape cleanup:

- For selected-implementation discovery entry points that currently accept
  `(context, body: ImplementationBody)`, make the selected lowering context
  the only required production input.
- Target the already migrated discovery families:
  backend type queries, backend value queries, backend intrinsic requests,
  backend/output source islands, source operations, backend control,
  generation variables, generation control, generation loops, mask keywords,
  and mask lane constants.
- Preserve token-only fallback internally by reading
  `context.implementation.body.tokens` only when
  `context.implementation.source_body_fragments` is absent.
- Keep existing `*_in_text(...)`, `*_in_fragments(...)`, and other narrow
  helper APIs when they are already text/fragment-specific and useful for
  focused tests.
- Update production callers and tests to use the cleaned selected-context API.
- Add focused static guardrails, likely in
  `tslgen/tests/test_m254_7_fragment_first_discovery_api_signature_cleanup.py`,
  proving the migrated discovery APIs no longer expose `body:
  ImplementationBody` signatures.
- Record exact remaining `ImplementationBody` references and use that
  accounting to select the next M254.x prompt.

## Non-Negotiable Guardrails

- No discovery semantic changes.
- No new TSIL keyword semantics or keyword spellings.
- No new parser, source scanner, or source repair path.
- No pairwise surrounding-keyword handlers.
- No backend rendering, generated-project build verification, template
  rendering, CLI workflow, primitive-call selector semantics, dependency
  closure semantics, assignment/index parsing, or target-language expression
  parsing.
- Do not remove the domain `ImplementationBody` class, catalog/pipeline
  compatibility body construction, lowerer direct-body compatibility view, or
  token-only test coverage in this milestone.
- Do not introduce runtime dependencies on `frozen` or `tslgenold`.
- Do not reactivate M255 while production body lowering still depends on
  `ImplementationBody`.

## Expected Tests

Add or update focused tests so the existing behavior remains covered:

- Existing token-only fallback tests for migrated discovery families should
  continue to pass through selected contexts without an explicit body
  parameter.
- Fragment-backed tests from M254.1-M254.6 should continue to prove fragments
  are preferred.
- A new static guardrail test should check the targeted production modules for
  absence of `body: ImplementationBody` selected-discovery signatures and
  absence of new source scanners, pairwise keyword paths, fixture-shaped
  pipelines, and runtime `frozen`/`tslgenold` dependencies.

## Out Of Scope

Changing discovery semantics, removing `ImplementationBody` from the domain
model, deleting catalog/pipeline compatibility construction, rewriting lowerer
direct-body compatibility views, deleting token-only tests, backend rendering,
generated-project build verification, primitive-call selector semantics,
dependency-closure behavior, source repair, target-language parsing,
