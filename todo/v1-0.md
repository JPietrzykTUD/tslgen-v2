## Decision summary

The v1.0.0 target should be the generated TSL C++/Rust library, not a promise
that `tslc` or the VS Code extension has independently reached version 1.0.0.
Their package versions and compatibility policies must remain explicit and may
stay on a `0.x` line.

The following are release gates:

1. integrate the completed unchecked/`*_checked` API design on a green current
   `main`;
2. provide full C++ support for the declared stable SVE, fixed-width SVE, and
   RVV surfaces;
3. make the supported C++ and Rust APIs, documentation, and consumer builds
   release-quality;
4. test the stated Rust MSRV and the supported compiler/platform matrix; and
5. make the release atomic, reproducible, immutable, and conditional on all
   required gates.

The central idea in the pre-v1.0 proposal—**implementation-aware SIMD
portability**—is a good product and research direction. The complete proposal is
not a good v1.0 release gate as written. It combines several research features,
new schemas, new generated public APIs, a contract language, compiler/editor UX,
and release stabilization into one critical path. It should be split into a
small v1 consolidation and an incremental v1.x roadmap.

## What “full C++ SVE/RVV support” means

This phrase needs a precise boundary. It must not mean “every instruction and
optional subextension in either ISA,” and it must not hide impossible API shapes
behind skipped generation.

For v1.0.0, full support means:

- the stable portable TSL callable surface and its type domain are enumerated by
  an exact, reviewed support contract;
- every expected SVE, SVE128, SVE256, SVE512, and RVV C++ specialization is
  selected and lowered, or is rejected by that public support contract before
  it enters the expected universe;
- the exact inventory contains no absent, unresolved, pruned, or
  policy-deferred stable slot;
- every emitted specialization has an explicit coarse implementation state;
  `fallback` and `unknown` are reviewed and disclosed rather than being counted
  as target-native quality;
- the explicitly named accelerated-core operations are native or composed from
  supported primitives, while target-neutral utilities may remain honest
  portable implementations;
- a scalar/generic fallback for an accelerated-core operation is allowed only
  as a reviewed, documented exception with correctness tests and performance
  evidence—it is never counted as native parity;
- ordinary and `*_checked` declarations, preconditions, documentation, and
  exact public-API manifests cover those profiles;
- full generated C++ projects compile warning-clean as normal includes, not only
  as system headers;
- generated value and differential tests cover all planned cases without hidden
  skips;
- the same scalable binary is exercised at multiple runtime vector lengths;
  and
- QEMU correctness evidence is supplemented by at least one native SVE run and
  one native RVV/CHORYS run before the final tag.

If native evidence cannot be obtained, the corresponding profile remains
explicitly experimental for that release; the gate is not waived silently.

Two qualifications are deliberate:

1. **Scalable SVE is a separate contract from SVE128/256/512.** Passing the
   fixed-width profiles does not prove a vector-length-agnostic implementation.
2. **Fixed-shape APIs cannot simply be promised for a runtime-sized vector.** A
   primitive whose public result is a compile-time-sized `std::array`, or whose
   input is a compile-time lane list, needs either an honest scalable buffer/view
   form or an explicit fixed-shape-only capability classification. Returning a
   heap container or inventing `Vec::vector_element_count` for scalable SVE is
   not an acceptable compatibility trick.

The v1 RVV scope should be the repository's declared RV64 V 1.0 profile with
ELEN=64 and the stable TSL scalar-type set. Optional extensions such as Zvbb,
every LMUL combination, and stable Rust RVV are separate capabilities unless an
existing stable TSL operation genuinely needs them. Likewise, the v1 SVE claim
does not imply SVE2.

I would not define full support as “every specialization is native.” That would
conflate semantic availability with implementation quality and would misclassify
legitimate target-neutral operations. The support gate proves complete,
correct, tested APIs. The exact realization ratchet separately prevents a
native/composed operation from silently degrading and makes every fallback or
unknown visible.

### Completed work that should not be redesigned

The checked-API refactor has passed its focused architecture review. It already
establishes:

- direct unchecked calls with no hidden sanitization;
- `*_checked` only for complete, representable catastrophic runtime
  preconditions;
- C++ direct vector return plus explicit `precondition_error&` for value results;
- idiomatic Rust `Result` and `unsafe fn` where required;
- typed call-precondition forwarding/discharge and fail-closed transitive

- compiler-owned editor projections.

The checked API is integrated and has completed its broad local release
validation. Remaining safety work is limited to target coverage discovered by
the later scalable-support slices, not a new safety design.

## Assessment of `pre-v1-0-todo.md`

### Findings, ordered by severity

#### High — the proposal is too large to be the v1 critical path

The proposal marks structured realization and contracts as P0, semantics and a
certificate as P0/P1, and a quality ratchet as P0/P1, then makes the combined
result a release gate
([proposal sections 1–5](pre-v1-0-todo.md#L46),
[milestones](pre-v1-0-todo.md#L976),
[release gates](pre-v1-0-todo.md#L1055)). That is multiple compiler products,
not one stabilization slice. It would force us to stabilize new schemas and
generated APIs before the existing library has closed its target, warning, CI,
and packaging gaps.

**Disposition:** accept the thesis and preserve the roadmap, but do not make
structured hazards, consumer contracts, a capability-certificate schema, or
rich generated realization APIs mandatory for v1.0.0.

#### High — the proposal understates how much typed infrastructure already exists

The proposal does acknowledge an existing implementation-state lattice and
dependency closure, but its milestone sequence still reads too much like a
greenfield model. Today the compiler already has:

- the public `native | composed | fallback | unknown` lattice in
  [`implementation_facts.py`](../tslc/src/tslc/lower/implementation_facts.py#L13);
- bottom-up propagation of safety, unresolved call preconditions, target
  features, compiler capabilities, and implementation state through the live
  call graph in
  [`_pipeline_closure.py`](../tslc/src/tslc/_pipeline_closure.py#L424);
- a frozen concrete specialization/dependency analysis in
  [`concrete_analysis.py`](../tslc/src/tslc/concrete_analysis.py#L37);
- deterministic `tslc analyze --format json` output in
  [`analyze_specialization.py`](../tslc/src/tslc/maintenance/analyze_specialization.py#L88);
- generated C++ and Rust implementation-state queries; and
- typed arithmetic, operation, memory, conversion, shift, safety, operand-role,
  and checked-precondition facts in the catalog/lowering pipeline.

**Disposition:** begin any v1.x realization work with a fact/owner inventory and
an explicit delta. Extend these owners; do not introduce a parallel realization
graph, semantic registry, or renderer-owned classification.

#### High — semantic facts and verification evidence cannot be one canonical certificate

The proposed certificate includes both deterministic compiler facts and
`compiled`, `executed`, `differentially_tested`, and `benchmarked` evidence
([certificate contents](pre-v1-0-todo.md#L532),
[evidence taxonomy](pre-v1-0-todo.md#L559)). Generation cannot truthfully claim
later toolchain or hardware runs, and those runs necessarily carry environment,
compiler, runner, and often time metadata. Combining them invites either stale
claims or a supposedly canonical file that changes after each run.

**Disposition:** when implemented, split this into:

1. a deterministic, versioned **semantic capability manifest** produced by the
   compiler from input identity, selection, lowering, closure, and backend
   facts; and
2. one or more **verification attestations** that reference the manifest digest
   and record compiler, flags, runner/hardware, test stage, result, and run
   metadata.

Schema compatibility should be versioned independently from generated-library
SemVer.

#### Medium — scalable support exposes a real mismatch in the proposed universal surface

Cross-profile parity cannot mean that fixed-size array/lane-list signatures are
silently instantiated for runtime-sized SVE/RVV values. The proposal correctly
calls for representation semantics, but it does not first define which API
shapes are meaningful for scalable vectors.

**Disposition:** freeze scalable shape capabilities before closing individual
primitive gaps. Reuse ordinary load/store or introduce caller-owned extent-aware
buffer/view forms where needed. Mark inherently fixed-shape callables as such in
the support contract. Do not manufacture a compile-time length, allocate a
container behind the user's back, or make renderers special-case primitive
names.

#### Medium — detailed hazards need stricter ownership than the proposal states

The proposal's “do not parse rendered C++/Rust” and “unknown rather than guess”
rules are correct
([structural-hazard rules](pre-v1-0-todo.md#L149)). However, a hazard such as
`temporary_buffer` belongs to a selected implementation, not to the primitive's
language-neutral operation semantics. Raw target text can also conceal it.

**Disposition:** derive hazards from typed TSIL region effects and lowered call
facts. If opaque implementation text must declare a fact, use a closed,
validated implementation-local annotation with `unknown_target_code` as the
fail-closed default. Do not put transitive or measured facts into primitive
definitions.

#### Medium — rich generated query APIs are premature for v1

The proposal asks C++ and Rust to expose structured realization objects
([generated-library queries](pre-v1-0-todo.md#L212)). Doing so before the hazard
and provenance vocabulary is empirically validated would add a large stable API
and code-size obligation. The current coarse implementation-state query already
provides a useful, bounded v1 surface.

**Disposition:** freeze and document the coarse state API for v1. Keep detailed
origin, dependency paths, requirements, and later hazards compiler-side until
their representation and size are proven. Add generated bitsets/traits in v1.x
only if a real compile-time consumer requires them.

#### Medium — parity must be scoped to declared backend capability

The proposal sometimes phrases C++/Rust parity as universal. Stable Rust does
not currently form part of the repository's RVV profile, and scalable Rust
intrinsics have a different maturity/toolchain contract.

**Disposition:** parity reports compare the declared support universes and say
`backend_unsupported` explicitly. C++ SVE/RVV completeness is a v1 gate; stable
Rust SVE/RVV is not silently added to it.

### Strong parts to keep

The following ideas are sound and align with the repository charters:

- implementation-aware portability is a credible differentiator;
- `native` must not be treated as “one instruction” or “fast”;
- structural hazards are observations, not an invented numeric cost model;
- exact dependency paths and provenance are more useful than aggregate counts;
- target features and compiler capabilities remain distinct;
- no arbitrary C++/Rust parsing or full target-language AST belongs in `tslc`;
- empirical work should validate whether structural facts predict real cliffs;
- workload-specific policies belong downstream; and
- dynamic dispatch and a general target-plugin framework should not delay v1.

The proposed `compress_store` experiment is a good research track, but its
performance result should not determine whether a correctness-focused v1 tag
can be cut.

### Where the proposed knowledge belongs

| Knowledge | Owner | Must not become |
| --- | --- | --- |
| Valid-call semantics and catastrophic preconditions | `tsldata` primitive declaration, promoted into typed catalog facts | backend prose or name inference |
| Direct implementation mechanism/hazard | typed TSIL region effect; narrowly, a validated implementation-local source annotation | a primitive-wide semantic claim |
| Direct calls and proof dispositions | typed lowering dependency edges | renderer reconstruction |
| Transitive dependencies, safety, requirements, state, hazards | compiler closure over live lowered specializations | duplicated source annotations |
| Target features and runtime vector-length capability | extension and machine-profile models | primitive-name conditionals |
| Compiler intrinsic/toolchain capability | backend-owned typed capability descriptors and probes | CPU-feature aliases |
| Consumer portability policy | project/consumer contract configuration | `tsldata` corpus policy |
| Build/run/value/differential/benchmark result | verification attestation referencing an input/manifest digest | deterministic source semantics |
| Editor display | compiler-owned LSP projection; thin VS Code presentation | client-side semantic inference |

## Ordered implementation slices

Each slice ends with its focused tests, the proportionate broader gate, a
diff/design review, fixes for findings, `git diff --check`, and one coherent
commit. A baseline update is part of a slice only when the exact semantic delta
has been reviewed; it is never used to conceal a regression.

### Slice 0 — Freeze the v1 product and support contract

**Outcome:** one reviewable statement defines what carries `1.0.0` and exactly
which generated surfaces are stable.

- Declare the generated C++/Rust library as the v1 product.
- Record independent compatibility/version policies for `tslc` and the editor.
- Enumerate stable backends, profiles, primitive declarations, algorithms,
  scalar types, mask/attribute variants, and checked companions through existing
  typed catalog/profile/support-policy owners plus the smallest explicit release
  policy. Do not hand-maintain a second specialization catalog.
- Classify target-specific callables and inherently fixed-shape callables rather
  than pretending they are portable scalable slots.
- Freeze the unchecked/`*_checked` contract and the meaning of the coarse
  implementation states.
- Name the accelerated-core operation set, decide the fallback policy described
  above, and require explicit exceptions.
- State that v1 C++ covers SVE, SVE128/256/512, and RVV V 1.0; it does not imply
  SVE2, every RVV optional extension/LMUL, or stable Rust SVE/RVV.

**Acceptance:** a machine-readable support declaration and human support matrix
name the same exact universe; incompatible claims in package metadata, docs, and
release workflows fail a test.

### Slice 3 — Add an exact target-support parity ratchet

**Outcome:** “100%” means every expected stable slot, including a slot for which
selection currently finds no candidate.

- Build the expected universe from the typed catalog, support declaration,
  machine profiles, backend support, scalar domains, signatures, masks,
  attributes, variants, and the real selector rules.
- Preserve the full logical identity: profile, backend, primitive declaration,
  signature, type, mask/attribute/variant, source extension, selected target
  extension, and conversion target where applicable.
- Classify `absent`, `selected`, `lowered`, `pruned`, `policy_deferred`, and
  `emitted`, plus `native | composed | fallback | unknown` for emitted slots.
- Keep generation/selection as the owner. The report is a compiler projection,
  not a second selector.
- Commit a compact canonical SVE/SVE128/256/512/RVV ratchet with reviewed
  exclusions carrying stable reason identifiers. It must preserve exact
  identities and produce human-readable diffs; an aggregate count or bare hash
  is insufficient.

**Acceptance:** a fixture with a completely absent target candidate fails the
ratchet; adding an unrelated primitive/profile family is additive; report and
generation identities are owner-equivalent and deterministically ordered.

### Slice 4 — Define scalable shapes and representation multiplicity

**Outcome:** the compiler can represent the scalable operations required by the
stable surface without lying about compile-time lane counts.

- Decide the public contract for `s[]`, `lanes<s>`, `to_array`, and `from_array`
  on runtime-length vectors.
- Prefer existing caller-owned load/store/span forms when they express the
  semantic operation; add a new typed scalable form only when the public
  capability is genuinely missing.
- Model runtime lane-count queries explicitly and remove scalable lowering's
  dependence on `value(vector::length)`.
- Add a typed register-group/multiplicity concept only for concrete conversion
  cases that require it. It may represent RVV LMUL or SVE tuple/group results,
  but must not become a speculative universal vector AST.
- Ensure backend dialects translate finalized shape/multiplicity facts while
  templates only format them.

**Acceptance:** no scalable specialization relies on a fabricated compile-time
lane count; fixed-shape-only APIs are diagnosed/classified before lowering; at
least one SVE and one RVV conversion case prove the extension point.

### Slice 5 — Close fixed-width SVE dependency leaks

**Outcome:** SVE128, SVE256, and SVE512 are independently generated profiles.

- Replace `extract` composition that calls `from_array` through smaller physical
  extension identities with an implementation/dependency shape valid inside
  the requested profile.
- Audit other fixed-SVE bodies for cross-profile calls hidden by inheritance.
- Keep dependencies semantic and typed; do not teach closure to emit unrelated
  physical profiles merely to make a body compile.

**Acceptance:** strict checks for SVE128/256/512 contain zero unsupported slots,
and a test rejects a future fixed-profile dependency leak.

### Slice 6 — Close scalable SVE semantic coverage

**Outcome:** every slot in the declared scalable SVE C++ universe exists and has
an honest implementation state.

- Implement lane access/mutation without routing through fixed arrays.
- Implement gather, scatter, and narrow-partial gather with runtime lane and
  mask semantics, including their checked extent/index contracts.
- Implement `convert_lanes` and any required representation changes using the
  Slice 4 model.
- Resolve the reviewed fixed-shape policy-deferred slots by implementing a
  scalable form or excluding an inherently fixed-shape callable in the public
  support declaration—not by suppressing diagnostics.
- Continue by dependency family: construction, masks, memory bridges,
  conversions, reductions, permutations, compression, and higher-level
  composition revealed by the exact ratchet.

**Acceptance:** `./dev.sh check --profile sve --backend cpp --strict` passes;
the exact parity ratchet has no absent/deferred stable slots and no unreviewed
fallback/unknown states; focused generated values cover runtime lane counts,
predicates, inactive/tail lanes, indices, conversions, alignment, and checked
failures.

### Slice 7 — Prove and close RVV semantic coverage

**Outcome:** RVV's apparent completeness becomes exact, tested completeness.

- Use the Slice 3 ratchet to discover candidates absent from today's attempted
  denominator.
- Close gaps in dependency order rather than adding isolated bodies: foundation
  and representation, reductions/counts, indexed memory, permutation,
  compression, and higher-level compositions.
- Audit use of runtime VL, SEW, masks/tails, signedness, widening/narrowing, and
  register multiplicity; forbid fixed-VLEN assumptions.
- Keep optional Zvbb implementations additive. Baseline V must retain a correct
  composed path where the stable surface requires the operation.
- Validate the CHORYS RISC-V integration kernel through generated TSL, including
  both ordinary and relevant checked paths.

**Acceptance:** the exact RVV ratchet has no absent/deferred stable slots and no
unreviewed fallback/unknown states; strict lowering passes; full generated
values pass at multiple VLENs; the CHORYS kernel agrees with a scalar oracle on
native hardware.

### Slice 8 — Make scalable-target verification exhaustive and reusable

**Outcome:** SVE/RVV support is backed by reproducible evidence rather than one
smoke primitive or workflow-specific commands.

- Generate and cross-build the full stable C++ corpus for SVE,
  SVE128/256/512, and RVV.
- Make every planned value/differential case a required result; a skip is a
  reported release gap.
- Add typed runner variants so the same scalable SVE binary runs at 128, 256,
  and 512 bits and the same RVV binary runs at VLEN=128 and VLEN=256 (and 512
  where supported). Remove the ad hoc RVV workflow branch once the verifier owns
  this matrix.
- Exercise edge semantics: partial VL where the public model admits it, tail and
  inactive lanes, masks, invalid checked inputs, indices, aliasing/alignment,
  integer overflow, floating conversion/rounding/NaNs, and width changes.
- Keep normal CI hardware-independent through injectable runners and explicit
  skips, but make native SVE and RVV evidence mandatory in the release-candidate
  checklist.
- Record semantic manifest digest, compiler and flags, emulator/CPU, vector
  lengths, and exact test outcomes in a verification attestation.

**Acceptance:** QEMU multi-VL results and native SVE/RVV reports reference the
same generated-input identity; no release claim treats emulator timings as
performance evidence.

### Slice 9 — Make the generated C++ product consumer-clean

**Outcome:** a normal downstream project can include every supported profile
without suppressing library warnings.

- Remove full-header unused-parameter, tautological unsigned comparison, and
  uninitialized-placeholder warnings identified by the post-review.
- Add normal-include warning gates for every declared compiler/profile pair,
  using GCC/Clang `-Wall -Wextra -Werror` where supported and MSVC `/W4 /WX`
  for applicable Windows/x86 profiles.
- Expand the external consumer beyond scalar and compile representative checked
  and unchecked operations for each stable architecture family.
- Extend exact C++ declaration baselines beyond today's reviewed scalar/AVX2
  scope to every stable v1 profile without hashing rendered source.
- Audit generated size and compile time as product risks; optimize only where a
  measured issue blocks distribution or use.

**Acceptance:** generated headers pass as ordinary includes across the compiler
matrix; system-include suppression is not counted as warning cleanliness.

### Slice 10 — Freeze the stable Rust surface and documentation quality

**Outcome:** the v1 Rust crate makes only support claims that stable toolchains
and generated tests prove.

- Test, rather than merely declare, `rust-version = 1.89` and record the stable
  compiler matrix.
- Freeze the opaque facade/re-export boundary and exact public declaration
  manifest for the supported profiles.
- Keep unsupported stable SVE/RVV profiles explicit; do not emulate parity with
  private LLVM intrinsics or scattered inline assembly.
- Run strict warnings, Clippy correctness/suspicious lints, Rustdoc missing-docs,
  doctests, package-content reproducibility, and external path-dependency
  consumers on the integrated tree.
- Preserve Rust's `unsafe` boundary for unchecked catastrophic preconditions and
  its idiomatic checked `Result` surface.

**Acceptance:** MSRV and current stable pass the supported build/value/doc
matrix; the packaged crate contents are independent of whether documentation
was built locally.

### Slice 11 — Consolidate implementation-aware v1 behavior without expanding it

**Outcome:** v1 accurately exposes and documents the implementation-awareness
already present in the compiler.

- Audit the owner and meaning of every existing implementation-state,
  dependency, feature, compiler-capability, safety, and semantic fact.
- Freeze/document the coarse C++ and Rust implementation-state query contract.
- Verify deterministic `explain`, `analyze --format json`, stage dump, and editor
  projections for representative native, composed, fallback, unknown, and
  unresolved cases.
- Make `unknown` explicit and fail closed where a release support contract
  requires a known state.
- Do not add structured hazard APIs, a consumer contract language, or a
  certificate schema in this slice.

**Acceptance:** documentation claims match typed compiler behavior, compiler
projections agree on the same concrete specialization, and the VS Code client
contains no duplicated semantic inference.

### Slice 12 — Reconcile v1 documentation and migration material

**Outcome:** generated references and maintainer/user documentation describe the
released product, not an intermediate refactor state.
