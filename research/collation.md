# Research finding: exact SIMD collation for columnar databases

**Assessment date:** 2026-08-08

**Proposal package:** [`collation/`](collation/README.md)

## Finding

The most promising outstanding database research direction identified for TSL
is **columnar semantic-key compilation**:

> Can a columnar database compile Arrow batches or Parquet dictionaries of
> UTF-8 strings into exact, versioned collation keys with a dynamically
> lane-refilled SIMD transducer, making locale-aware filtering, grouping,
> joining, and sorting approach binary-string performance across fixed- and
> scalable-vector CPUs?

This is stronger than a generic Arrow/Parquet decoder or a general
SIMD/SIMT/FPGA-library claim. Exact collation is a real database semantic: it
determines equality and order under language- and locale-specific rules. It is
also expensive enough that DuckDB's documentation describes binary comparison
as “[by far the fastest](https://duckdb.org/docs/lts/sql/expressions/collations)”
choice while relying on ICU for regional collations.

## Proposed mechanism

Process several independent strings at once, with one logical string per SIMD
lane. Each lane maintains its own byte cursor, collation level, context, pending
expansion, and output state. Masks identify finished and exceptional lanes;
finished lanes are refilled from the batch so that short strings do not remain
idle behind long strings.

The transducer produces only conservative exact products:

- a bounded ordering prefix that decides order only when it contains the first
  proven distinguishing byte;
- an equality-compatible fingerprint where a mismatch proves inequality but a
  match still receives exact collision comparison; or
- a complete semantic key when repeated use amortizes its memory cost.

Contractions, expansions, normalization, numeric collation, unsupported table
entries, output overflows, and other cases outside the proven vector domain are
routed to the same pinned ICU collator as the baseline. The combined path must
return exactly the ICU result.

## Why Arrow and Parquet fit

Arrow strings expose offsets and a UTF-8 data buffer, a natural batch interface
for cross-string SIMD. Arrow and Parquet dictionaries expose a different
opportunity: compile each distinct value once, then reuse its semantic prefix,
fingerprint, full key, or local order rank for every occurrence.

Raw dictionary IDs are not semantic keys. They may be page-local, arbitrarily
assigned, and incomparable across dictionaries. Every derived product must be
scoped by the exact dictionary contents and collation identity; plain-encoded
fallback pages must remain correct.

This makes Arrow/Parquet physical placement an experimental factor rather than
the novelty claim. “A SIMD Parquet decoder generated by TSL” is already too
close to production engineering and occupied research. The open question is
when a new exact semantic transformation should be performed and reused.

## Why the question is not already answered by the closest work

- [Unicode UTS #10](https://www.unicode.org/reports/tr10/) and
  [ICU](https://unicode-org.github.io/icu/userguide/collation/) already define
  collation and sort keys. The proposal does not claim to invent them.
- [ICU's architecture](https://unicode-org.github.io/icu/userguide/collation/architecture.html)
  already includes optimized Latin handling, partial keys, and key reuse. ICU
  is therefore a strong baseline, not a naive scalar straw man.
- [DuckDB's sorting work](https://hannes.muehleisen.org/publications/ICDE2023-sorting.pdf)
  vectorizes normalized database-key construction, but says that string
  collation is evaluated before the string prefix is encoded. The proposed work
  targets that preceding semantic transformation.
- [Unicode at Gigabytes per Second](https://arxiv.org/abs/2111.08692) shows that
  SIMD can validate and transcode Unicode quickly, but does not implement
  locale tailoring, multi-level collation weights, contractions, expansions,
  or relational equality/order.
- The Arrow project has a longstanding
  [collation feature request](https://issues.apache.org/jira/browse/ARROW-12046),
  demonstrating demand but not an exact vectorized database result.
- A draft [Apache Iceberg collation proposal](https://github.com/apache/iceberg/pull/16972),
  inspected on 2026-08-08, makes collation identity and version relevant to file
  bounds while deliberately limiting broader equality, hashing, partitioning,
  and sort semantics. That leaves efficient execution open and makes versioned
  semantic data topical.

The preliminary search did not find a publication or open implementation that
combines exact cross-string SIMD collation, lane refill, format-aware reuse, and
real relational operators. This is not proof of novelty. The first project gate
must audit papers, theses, patents, and production source; an equivalent result
ends or narrows the claim before substantial implementation.

## Falsifiable hypotheses

- On realistic corpora from at least three language/script families, the exact
  TSL SIMD path plus fallback is at least **1.8x faster** than the strongest ICU
  method producing the equivalent product.
- At least two structurally different collated operators improve by at least
  **15%** end to end.
- Cardinality, reuse, string length/skew, ambiguity, and collation complexity
  yield repeatable regions where transient Arrow, per-dictionary, full-key, or
  direct-ICU execution wins.
- One semantic state machine and key/table format remains useful on at least two
  materially different vector families; a scalable-vector claim requires real
  SVE or RVV hardware.

The idea is falsified as a broad database paper if ICU is already near the
attainable limit, non-ASCII exception rates are high, table gathers dominate,
lane refill does not offset state movement, key memory erases query gains, no
operator reaches the end-to-end threshold, or each ISA needs an algorithm fork.

## Genuine role of TSL

The proposed algorithm needs masked gathers, predicate manipulation,
compress/expand or equivalent refill, population counts, vector-length-aware
tails, and bounded output. The repository already contains candidate primitives
in
[`rnd_access.tsl`](../tsldata/primitives/load_store/rnd_access.tsl),
[`pack_expand.tsl`](../tsldata/primitives/load_store/pack_expand.tsl),
[`compress_expand.tsl`](../tsldata/primitives/misc/compress_expand.tsl), and
[`bitwise.tsl`](../tsldata/primitives/mask/bitwise.tsl).

Their existence does not prove native or performant support on every profile;
the prototype must inventory the exact generated closure. TSL is the instrument
that holds the semantic algorithm constant while the vector realization
changes. The database algorithm and placement result—not the fact that code was
generated—are the paper contribution.

Broadening TSL to a general SIMD/SIMT/FPGA library should not precede this
pilot. A GPU or FPGA follow-on is justified only if the CPU study exposes a
stable semantic operation whose lookup, scheduling, and emission contract
survives the different execution model.

## Recommendation

Run the first four kill gates only:

1. claim/prior-art audit;
2. profiling that proves collation is a material wall in at least two real
   operator families;
3. an exact scalar fast-domain prototype with substantial non-ASCII coverage;
4. one TSL SIMD kernel that clears the ICU and same-algorithm scalar thresholds.

Do not build a full DBMS integration, Parquet path, or new accelerator backend
until those gates pass. The detailed design, implementation sequence, and
evaluation protocol are in:

- [`collation/technical-proposal.md`](collation/technical-proposal.md)
- [`collation/plan-implementation.md`](collation/plan-implementation.md)
- [`collation/plan-evaluation.md`](collation/plan-evaluation.md)
