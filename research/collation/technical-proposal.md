# Technical proposal: exact semantic-key compilation for columnar strings

## Objective

Build the smallest system that can determine whether exact locale-aware string
semantics can become a first-class columnar transformation instead of a scalar
library call at every comparison.

The proposed system should:

1. consume UTF-8 strings in Arrow-compatible offset/data form or from a
   Parquet/Arrow dictionary;
2. construct safe ordering prefixes, equality-compatible fingerprints, or
   complete semantic keys across several independent strings at once;
3. dynamically refill SIMD lanes as variable-length strings finish or leave the
   vector fast domain;
4. guarantee the same equality and ordering as one pinned ICU configuration;
5. expose unresolved cases explicitly and resolve them with ICU;
6. integrate the products into real relational operators; and
7. instantiate one semantic implementation for fixed- and scalable-vector
   profiles through TSL.

The system is a research prototype. It is not a replacement for ICU, a new
Unicode standard, a complete Parquet reader, or a generic database engine.

## Research boundary and ownership

The collation prototype should be an independently owned downstream consumer of
the generated TSL C++ product. It owns:

- the collation identity and semantic contract;
- versioned lookup-table construction;
- Arrow and Parquet adapters;
- per-lane transducer state;
- safe-prefix, fingerprint, and full-key formats;
- ICU fallback and differential testing;
- operator integration and placement policy;
- workload generation, measurements, and result records.

`tslc` and `tsldata` continue to own primitive semantics, target/profile
selection, dependency closure, code generation, and verification. They must not
learn about ICU, Arrow, Parquet, or database collation. The prototype must call
the public generated API and must not parse generated C++, TSIL bodies, or
intrinsic spellings.

If a generally useful primitive is missing, it should be proposed and validated
as a separate projection-neutral TSL change. The research prototype must not
smuggle an application-specific operation such as `collate_utf8` into the core
primitive corpus merely to simplify the experiment.

## Semantic contract

### Collation identity

Every derived product must be scoped by a complete immutable identity. At
minimum it contains:

```text
CollationIdentity
  provider                 # ICU for the primary experiment
  provider_version
  unicode_data_version
  cldr_data_version        # when relevant
  locale_or_tailoring_id
  tailoring_digest         # for explicit rules
  strength
  normalization_mode
  case_level_and_order
  numeric_mode
  alternate_handling
  reorder_codes
  semantic_key_format_version
```

Fields that do not apply are recorded explicitly rather than silently omitted.
Two semantic products may interact only when their identities and key-format
versions match exactly. A mismatch selects recomputation or ICU; it never falls
back to comparing incompatible bytes.

This rule is stricter than an ordinary cache tag because collation changes can
alter both equality and order. ICU likewise warns that sort keys generated by
different algorithms, data tables, or collators must not be compared as though
they were compatible.

### Input contract

The initial input is a nullable Arrow-compatible UTF-8 array:

```text
validity bitmap | offsets[0..n] | utf8_bytes[0..offsets[n])
```

The prototype must define one of two explicit invalid-UTF-8 policies:

- require a valid Arrow UTF-8 array and reject invalid input; or
- validate and route invalid rows according to the host engine's error policy.

It must never read past a string boundary while performing a masked gather.
Null ordering and SQL three-valued logic are handled by the consuming operator,
not encoded as a Unicode collation rule.

The dictionary input is:

```text
dictionary UTF-8 array | integer codes | optional validity bitmap
```

Codes are meaningful only relative to that dictionary. Parquet dictionary IDs
are not assumed to preserve lexical or collation order, and codes from different
pages or files are not assumed to identify equal values.

### Output products

The prototype supports three products so that it can measure the boundary
between recomputation and materialization.

#### Exact ordering prefix

For row `r`, the product contains:

```text
prefix[r, 0:P] | prefix_length | complete | fast_domain | collation_identity
```

The prefix is taken from a canonical byte stream whose lexicographic comparison
has been proved equivalent to the configured collator for the admitted fast
domain. It need not be byte-for-byte identical to ICU's internal sort-key
format, although using the ICU encoding for the first prototype may simplify
validation.

The comparison rule is conservative:

1. If two exact prefixes first differ before either is truncated, that byte
   determines order.
2. If a complete key terminates within the prefix and the other exact stream
   has a later byte, the documented terminator semantics determine order.
3. Otherwise the comparison is unresolved and uses a longer/full key or ICU.

No zero padding, truncation marker, or uninitialized byte may accidentally
decide order.

#### Equality-compatible fingerprint

The transducer may hash the complete canonical collation stream while it is
generated. The fingerprint contract is:

- collation-equal strings under one identity must produce the same
  fingerprint;
- different fingerprints prove inequality;
- equal fingerprints do not prove equality and require exact key or ICU
  comparison.

The hash seed and algorithm are part of the artifact manifest. Database hash
tables may use the fingerprint to select a bucket, but collision resolution
must retain exact semantics.

#### Complete semantic key

A complete key is binary-comparable under one identity and supports exact
equality and order without revisiting the original string. It is worthwhile
only when repeated comparisons amortize generation and memory traffic. Complete
keys are expected to be most useful for dictionaries, large sorts, and reused
build-side join keys.

### Stable ordering is separate

Collation can make distinct strings equivalent at the requested strength. A
stable sort or total database order may then use row position, the original
binary string, or another engine-defined tie-breaker. That tie-breaker must be
represented separately; it must not silently strengthen collation equality.

## System structure

```text
Unicode/CLDR data + pinned ICU configuration
                    |
                    v
       versioned collation-table compiler
                    |
                    v
Arrow strings ---> lane scheduler ---> TSL SIMD transducer
     |                    |                 |
     |                    |                 +--> exact prefix / stream hash
     |                    |                 +--> complete fast-domain key
     |                    +--------------------> exception row queue
     |                                           |
     +-------------------------------------------+--> pinned ICU fallback
                                                        |
                                                        v
                               filter / group / join / sort consumer

Parquet dictionary ---> compile each distinct entry once ---> code indirection
Parquet plain values ---------------------------------------> Arrow batch path
```

The reference and candidate paths share the same input, collation identity, and
operator semantics. A row carries a status saying whether its result is complete
and proven, not merely whether a SIMD function ran.

## Versioned collation-table compiler

The runtime kernel needs compact, gatherable data rather than a tree of locale
objects. A prototype-owned table compiler should generate it from authoritative,
pinned Unicode/CLDR inputs and public ICU behavior. It should not depend on
undocumented ICU memory layouts.

For every admitted code point or context, generated data records:

- UTF-8 decode class and byte length;
- whether normalization/context inspection is required;
- collation elements or an index into an expansion sequence;
- contraction-start and look-ahead metadata;
- non-zero weights by configured level;
- whether numeric, variable, reordering, or other option-specific handling is
  needed;
- a conservative `fast`, `needs_context`, or `fallback` classification.

The first table need not support every Unicode code point. It must, however,
make absence explicit and route it to ICU. A useful pilot progression is:

1. root collation with a proven simple-code-point domain;
2. one Latin tailoring including a nontrivial contraction or expansion;
3. at least two additional script/language families;
4. only then broader tailoring and option coverage.

For the initial simple domain, public ICU collation-element iteration can serve
as an oracle while authoritative data supplies provenance. Before publication,
the table builder must have a reproducible source-data story and an independent
validation path; a giant hand-copied table or snapshot of private ICU state is
not acceptable.

## Lane-refilled SIMD transducer

### Per-lane state

Each lane represents one logical string and maintains:

```text
row_id
begin, cursor, end
collation_level
context_state
pending_expansion_index, pending_expansion_count
output_prefix_cursor
stream_hash_state
complete_key_cursor            # only for the full-key mode
status                          # active, finished, exception, null
```

Fixed-size state should remain in vectors or small structure-of-arrays buffers.
Variable output belongs in batch-owned arenas. Original row boundaries remain
available so any exception can restart safely in ICU; partially emitted output
from that row is discarded unless its validity has already been proved.

### Scheduler

The scheduler maintains an `active_mask` and a monotonically increasing
`next_row`. It must evaluate at least three strategies:

1. **no refill:** process one vector of strings until every lane finishes;
2. **masked refill:** insert new rows into finished lane positions;
3. **compact and refill:** compress live lane state to the front and load a
   contiguous suffix of new rows.

The third form is the central proposal because it turns variable-length skew
into explicit data movement. It is not assumed to win. On an ISA where
compaction is expensive, masked refill may be better; this can be a primitive-
level realization difference while the semantic state machine stays unchanged.

The scheduler records active-lane occupancy, refill count, compaction cost,
strings completed per iteration, and exception occupancy. These measurements
are needed to explain results rather than simply reporting throughput.

### One iteration

A conceptual iteration is:

1. form a mask of lanes that need the next input symbol;
2. gather enough bytes to classify and decode one UTF-8 code point without
   crossing a row boundary;
3. classify each decoded value as simple, context-sensitive, expansion,
   normalization-sensitive, numeric, finished, or unsupported;
4. gather the corresponding collation-element metadata;
5. emit or hash weights for the lane's current level;
6. advance cursors, pending expansions, and context state;
7. mark completed and exception lanes;
8. compact/refill state according to the selected scheduler;
9. repeat until all rows have an exact product or are queued for ICU.

Masked loads must be genuinely safe on every target; a false lane may not point
outside an allocated buffer merely because one x86 implementation suppresses a
fault.

### Multi-level key construction

Collation keys are level-major: all primary weights precede secondary weights,
which precede tertiary and optional later levels. The prototype should compare
two implementations:

- **bounded per-level buffers:** collect weights for several levels in one input
  pass, then concatenate them; and
- **level-major rescans:** retain small state and rescan the cached string for
  each required level.

The rescan design is the simpler correctness baseline. Bounded buffers may win
for short strings but can increase register pressure and spill traffic. A fixed
ordering prefix often completes within primary weights, so later levels should
be generated lazily when the consumer does not need them.

French backwards secondary weights, discontiguous contractions, normalization
that crosses the simple domain, identical strength, and complex custom
tailorings may initially select ICU. They become fast-path work only when their
frequency makes them scientifically important. Numeric collation must not be
approximated by bytewise digit handling.

### Exception handling

Exception handling is part of the algorithm, not an embarrassing corner:

- mark the row and retain its original offset range;
- discard any unproven partial product;
- compact exception row IDs into a batch queue;
- call the same pinned ICU collator used by the baseline;
- merge the exact result into the output product;
- count the reason and cost.

Reasons should distinguish unsupported script/table entry, contraction,
normalization, numeric mode, output overflow, invalid UTF-8, and internal
capacity limits. A single undifferentiated “slow path” counter cannot explain
coverage or guide future work.

## Arrow placement

Arrow provides a natural transient boundary:

- offsets load contiguously when a new group of lanes is filled;
- byte cursors diverge and use masked gathers thereafter;
- result arrays stay aligned with logical row IDs even after lane compaction;
- validity is consumed separately;
- prefix and fingerprint buffers can be batch-local and released with the
  operator's data chunk.

The adapter should accept Arrow-compatible buffers without copying the string
payload. A copied/repacked input may be evaluated as an explicit alternative,
but its conversion cost must be charged to the candidate.

For Arrow dictionary arrays, semantic products are attached to the immutable
dictionary instance and collation identity. Cache lookup must include a content
digest or stable dictionary identity; pointer reuse alone is unsafe.

## Parquet placement

Parquet is not a required input to the kernel. It supplies a valuable reuse
experiment:

1. a production reader exposes one string dictionary and its index stream;
2. the prototype compiles dictionary entries through the same Arrow-string
   kernel;
3. it stores per-entry prefix, fingerprint/full key, optional local order rank,
   and status;
4. the scan maps integer codes to this metadata;
5. plain-encoded pages use the ordinary Arrow batch path.

Important invariants are:

- local dictionary rank is valid only for that dictionary and collation
  identity;
- two entries with different original bytes may be collation-equal;
- equality grouping must merge such entries after exact confirmation;
- dictionary fallback within a column chunk is legal and must not change
  results;
- dictionary compilation, cache validation, and code-to-metadata gathers are
  included in measured cost;
- persisted products are out of scope until provider/version invalidation has
  been demonstrated.

The experiment should use standard Parquet files produced by at least two
independent writers. No target-specific re-encoding of the file may be called a
Parquet result.

## Relational consumers

### Equality and range filters

Compile constants once. A fingerprint mismatch can reject equality; a match
uses a complete key or ICU. Ordering prefixes can decide `<`, `<=`, `>`, and
`>=` only when the first exact difference is present. Unresolved rows are
compacted for exact comparison.

### `GROUP BY` and `DISTINCT`

Use the semantic fingerprint as the hash-table hash or as an input to the
engine's hash combiner. Within a bucket, compare complete keys or call ICU.
Different dictionary entries that collate equal must reach compatible buckets
and merge into one group. Representative-value selection follows the engine's
existing semantics.

### Hash join

Build and probe sides must use the same collation identity and fingerprint
algorithm. Full build-side dictionary keys may be retained when reuse is high.
Hash collisions and collation-equivalent but byte-distinct strings require
exact comparison. A version or configuration mismatch is an error or a
recompilation boundary, never a silent non-match.

### `ORDER BY`

Insert the semantic ordering prefix ahead of the rest of the engine's normalized
tuple key. Prefix ties call a longer-key or ICU comparator. Compare three modes:
direct ICU comparison, bounded prefix plus fallback, and complete-key
materialization. Stable or total tie-breaking remains engine-owned.

The first integration should choose the operator with the largest measured
collation fraction rather than assuming sorting is best. A second, structurally
different consumer is required for the full paper claim.

## Placement policy

The policy question is intentionally small. Candidate choices are:

```text
direct ICU comparison
transient batch prefix/fingerprint
full per-row key
per-dictionary prefix/fingerprint
full per-dictionary key or local rank
```

Candidate features are available without running the full query:

- row count and batch size;
- estimated or known distinct count;
- dictionary presence and reuse count;
- byte-length distribution and skew;
- sampled fast-domain/exception rate;
- sampled prefix-tie rate;
- number and kind of downstream consumers;
- configured collation strength/options;
- vector profile and measured table working-set class.

Begin with transparent thresholds or a shallow decision tree. The policy is
interesting only if multiple candidates win in repeatable regions and the
simple policy has materially lower regret than one fixed choice. A learned
black-box optimizer is not justified by a small plan space.

## TSL realization

The current TSL corpus already contains candidate building blocks:

| Algorithm need | Candidate TSL support |
| --- | --- |
| indirect byte/metadata access | `gather`, masked `gather`, and related narrow gathers in [`rnd_access.tsl`](../../tsldata/primitives/load_store/rnd_access.tsl) |
| compact or expand lane state | `compress`, `expand`, `compress_store`, and `expand_load` in [`compress_expand.tsl`](../../tsldata/primitives/misc/compress_expand.tsl) and [`pack_expand.tsl`](../../tsldata/primitives/load_store/pack_expand.tsl) |
| active counts and output positions | `mask_population_count` and mask operations in [`bitwise.tsl`](../../tsldata/primitives/mask/bitwise.tsl) |
| ordinary decode and weight operations | loads, shifts, comparisons, blends, arithmetic, and stores from the existing corpus |

Before coding the kernel, generate and verify the exact primitive slice for each
candidate profile. Record whether every dependency is native, composed,
fallback, unsupported, or unknown. Do not describe source-level availability as
native hardware support.

The C++ application owns the outer state machine. TSL operations implement its
vector steps. This keeps the research logic traceable and avoids requiring
`tslc` to understand arbitrary control flow or database types.

## Fixed- and scalable-vector behavior

The same semantic source should not assume a constant lane count. It asks the
generated TSL product for the profile's lane count or uses a vector-length-aware
loop, constructs valid predicates for the batch tail, and terminates based on
active state.

Portability does not mean identical instruction sequences. It permits a TSL
primitive to use native compaction on one ISA and a composition on another. It
does not permit:

- a different fast-domain definition;
- a different collation table or key format;
- dropping exact fallback on a difficult target;
- changing from lane refill to a target-specific algorithm without reporting an
  algorithm fork;
- performance claims from emulation rather than real hardware.

Correctness can be tested under emulation. Performance portability requires
real fixed- and scalable-vector CPUs.

## Correctness obligations

The implementation is admissible only if all of the following hold:

1. every fast-path ordering decision has the same sign as ICU;
2. every pair ICU considers equal has the same semantic fingerprint;
3. fingerprint collision handling cannot merge unequal values;
4. a prefix tie never decides an unresolved order;
5. dictionary remapping preserves equality and order within its declared scope;
6. keys are never reused across collation identities or key-format versions;
7. null, invalid UTF-8, and tie-breaking behavior matches the host engine;
8. buffer tails, empty strings, and masked memory operations are safe on every
   profile;
9. any unsupported condition reaches ICU rather than an approximate path; and
10. all operator outputs match a scalar/reference-engine result.

The evaluation plan turns these obligations into differential, conformance,
fuzz, and end-to-end tests.

## Expected failure modes

The proposal should be stopped or narrowed if:

- authoritative table construction is effectively a reimplementation of all of
  ICU before a useful fast domain exists;
- multilingual input triggers fallback too often for SIMD work to matter;
- lookup tables do not fit useful cache levels and gathered access dominates;
- lane-state compaction costs more than it saves under realistic length skew;
- multi-level output or complete-key allocation dominates Unicode processing;
- ICU's direct comparator already wins because most comparisons stop early;
- dictionary cardinality is too high or reuse too low to amortize compilation;
- prefix ties are common on realistic sort/group keys;
- memory growth, cache pressure, or version invalidation erases query gains;
- different ISAs require different semantic algorithms; or
- the closest-prior-art audit finds the main mechanism already disclosed.

Each failure yields a publishable claim only if it is systematic and explains a
previously unknown database/hardware boundary. A slow prototype by itself is not
a negative-result paper.

## Deliberate non-goals

- claiming the first collation key, normalized key, vectorized string operator,
  or optimized Latin collator;
- supporting every ICU option in the first prototype;
- replacing ICU as the correctness authority;
- changing Arrow, Parquet, or Iceberg specifications;
- persisting unversioned keys in Parquet files;
- treating dictionary IDs as global semantic keys;
- building a complete query optimizer;
- adding GPU, SIMT, or FPGA backends before the CPU mechanism survives its
  gates;
- modifying `tslc` or `tsldata` without an independently justified TSL need.

## What a successful result would explain

A strong paper should explain more than a single speedup. It should identify:

- which collation features admit a high-coverage conservative SIMD domain;
- whether lane refill solves real variable-length divergence;
- when prefixes, fingerprints, or complete keys are the right physical product;
- when a dictionary changes the optimal placement;
- how much binary-versus-collated performance can be recovered in relational
  operators;
- which vector primitives and machine properties control the result; and
- whether the same semantic algorithm is genuinely portable across fixed and
  scalable vectors.

Those findings would make TSL indispensable to the experiment without making
TSL itself the answer to the database research question.
