# TSL-Generator Middleend

This directory contains the source code for the TSL-Generator middleend, which is responsible for transforming the intermediate representation generated by the frontend into a form that can be easily consumed by the backend for code generation.
The middleend performs various transformations and optimizations on the intermediate representation, including dependency analysis, filtering, and TSIL rewrites.
Those transformations happen in parallel using python multiprocessing.

## Steps

### 1. Dependency Analysis

The middleend performs dependency analysis to determine the dependencies between different TSL primitives and their implementations.
This is crucial for determining the order of code generation and ensuring that all necessary components are generated correctly and included in the final output.
Dependencies are detected based on the `implementation` field of TSL primitives.
In particular, if a TSL primitive implementation contains a `call<primitive=PRIM>` statement, it is considered to have a dependency on the primitive `PRIM`.
Other types of dependencies may be added in the future, but currently only `call` statements are considered for dependency analysis.
Every worker process constructs a local dependency tree where nodes represent TSL primitives and edges represent dependencies between them.
As multiple primitives can have no dependencies but are needed by other primitives, we would end up in a forest of dependency trees rather than a single tree.
To mitigate the issue of having multiple trees, we introduce a dummy root node that represents the generation goal (e.g., `generate code for primitive X`), and all primitives that are needed to achieve that goal are connected as child nodes to the dummy root node.
Those local dependency fo are then merged into a global dependency graph in the main process.
Finally, the middleend performs a topological sort on the dependency graph to determine the order of code generation for the TSL primitives and their implementations and detects any circular dependencies that may exist. 
The final ordered is stored in the [GenerationContext](../core/context.py) for further processing by the backend components.

### 2. Requirement-Imputation

Based on the dependencies detected in the previous step, the middleend performs requirement-imputation to ensure that all necessary requirements for TSL primitives and their implementations are properly propagated and accounted for.
This is done by traversing the dependency graph from root to leaves and merging the requirements of the nodes along the path. 
Every node in the dependency graph has a `requires` field that specifies the required hardware features for that primitive implementation as a list of strings. 
When traversing the dependency graph, the middleend merges the `requires` fields of the nodes along the path by taking the union of the required hardware features.
This ensures that if a TSL primitive implementation depends on another primitive implementation that requires certain hardware features, those requirements are properly propagated and accounted for in the final generation context.

_IMPORTANT NOTE_: This stage only works with the requirements specified in the TSL primitive data files. It does not perform any additional requirement inference based on the implementation code or other factors. This would require a more sophisticated analysis and is left for future work.

### 3. Filtering

After dependency analysis and requirement-imputation, the middleend performs filtering to remove any TSL primitives and their implementations that are not needed for code generation.

We distinguish between two types of filtering: hard filtering and soft filtering.
Hard filtering means that if a TSL primitive implementation is filtered out, it will not be considered for code generation and any primitive implementation that depends on it will also be filtered out.
Soft filtering means that if a TSL primitive implementation is filtered out, it will be marked for filtering but will still be considered for code generation if it is a dependency of another primitive implementation that is needed for code generation.
The distinction between hard and soft filtering is important because it allows us to have more flexibility in specifying the filtering criteria while still ensuring that all necessary components are generated correctly and included in the final output.
The middleend keeps track of the filtering decisions and their reasons, and this information is included in the final generation report to provide better feedback to the user and aid in debugging any issues that may arise during the generation process.

The choreography of the filtering process is done by the [FilterPass](tsl_filter_pass.py) class, which applies the filtering criteria in a specific order to ensure that the filtering decisions are consistent and correctly propagated through the dependency graph.

In order to speed up the filtering process, the FilterPass starts from the leaf nodes of the dependency graph and works its way up to the root node.
This way, we can quickly filter out large portions of the dependency graph without having to traverse the entire graph for every filtering criterion.


#### Hard Filtering

##### Hardware Based

The available (or anticipated for cross-platform generation) hardware features are provided through the cli (`(--hardware-mode explicit --hardware-flags ...)|(--hardware-mode auto-detect)`) and are stored in `GlobalContext` ([context.py](../core/context.py)).

#### Soft Filtering

##### File Based

The cli allows users to specify a list of TSL files that should be included in the generation process (`--primitive-files ...`).
If a TSL primitive implementation is defined in a file that is not included in the specified list, it is marked for filtering. 

##### Primitive Name

The cli allows users to specify a list of primitive names that should be included in the generation process (`--primitives ...`).
If a TSL primitive implementation has a primitive name that is not included in the specified list, it is marked for filtering.

##### Extension Based

The cli allows users to specify a list of extensions that should be included in the generation process (`--extensions ...`).
The filtering process works similarly to file-based filtering, where if a TSL primitive implementation has an extension that is not included in the specified list of extensions, it is marked for filtering.

### Type Based Filtering

The cli allows users to specify a list of types that should be included in the generation process (`--types ...`).
The filtering process works similarly to file-based filtering, where if a TSL primitive implementation has a type that is not included in the specified list of types, it is marked for filtering. 


### 4. TSIL Rewrites

After filtering, the middleend performs TSIL rewrites to transform the intermediate representation into a form that can be easily consumed by the backend for code generation.
This stage mostly involves transforming the TSIL code in the `implementation` field of TSL primitives to a more canonical form that is easier to generate code from.
